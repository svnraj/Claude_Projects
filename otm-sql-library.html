Oracle Transportation Management · SQL library

One shelf, three ways to find what's on it.

Folders alone can't answer "which query do I reach for" — a query lives in a module and gets used for a purpose and gets reached for at some frequency. This framework picks OTM module as the folder you open, task type as a tag you scan for, and a one-page index as the net that catches everything the folders can't sort on their own.

01The organizing idea

Three layers, each doing one job. None of them works alone — together they cover "where do I look" and "how do I know this is the right one" at the same time.

Layer 1

Folder = module

The physical location. You already think "I need a rate query" before you think anything else, so the top-level folder matches that instinct.

Layer 2

Filename = task type

A tag baked into the name itself. Inside Rate, a DEBUG query and a REPORT query look nothing alike at a glance — the name should say which before you open it.

Layer 3

Index = everything else

Frequency, environment, last-verified date, the ticket it was written for. Things that don't deserve their own folder but absolutely deserve to be searchable.

02Folder structure

One folder per OTM domain, plus three utility folders that almost every query library ends up needing.

otm-sql/
├── order/
├── shipment/
├── tender/
├── rate/
├── fleet/
├── invoice-billing/
├── party-location/
├── integration/ interfaces, EDI, XML/CSV in-out, gateway logs
├── admin-config/ domain setup, user/role, workflow, agents
├── _utility/ reusable snippets, lookups, date helpers
├── _archive/ superseded or environment-retired queries
└── INDEX.md the master catalog — see section 06
Order Shipment Tender Rate Fleet Invoice / Billing Party / Location Integration Admin / Config

A query that genuinely spans modules (e.g. an order-to-invoice reconciliation) lives in whichever module it's run against most often — then gets both modules recorded as tags in the index, so it still surfaces under either.

03File naming

The filename should tell you what it is before you open it. One fixed shape, four parts:

rate​_FIX​_missing-fuel-surcharge-on-lane​_20260814.sql
module
matches the folder it sits in — makes the file self-identifying if it's ever copied or shared out of context.
task type
one of the fixed tags from section 04, always uppercase so it's easy to scan a directory listing.
description
lowercase, hyphenated, verb-first when possible — "find-", "reset-", "count-" reads faster than a noun phrase.
date stamp
YYYYMMDD of last meaningful edit, not creation — lets you sort a folder newest-first and see what's still fresh.

04Task-type tags

Keep this list short and fixed — the value of a tag comes from never inventing a new one on the fly.

TagUse it forTypical run frequency
MONITORHealth checks you'd run on a schedule — stuck orders, failed tenders, queue backlogs.Daily / on-call
DEBUGDiagnostic digging for a specific incident — tracing one order or shipment through its lifecycle.As-needed
REPORTScheduled or recurring extracts for a stakeholder — volumes, SLA, spend.Weekly / monthly
ADHOCOne-off analysis for a question that came up once. Candidate for _archive after use.Once
FIXData-correction scripts — read carefully before rerunning; note the environment in the header.Rare, high-caution
INTEGVerifying data made it across an interface — EDI, XML, integration gateway.Per incident / cutover
SETUPConfig and reference-data checks — domain values, user setup, workflow rules.During implementation

05File header template

Paste this as a comment block at the top of every query. It's what makes the file self-explaining even outside its folder, and it's the text a search tool actually matches against — see section 07.

header-template.sql
/* ------------------------------------------------------------
   PURPOSE   : One line — what question this answers
   MODULE    : RATE
   TASK TYPE : FIX
   TABLES    : RATE_RECORD, RATE_OFFERING
   ENV       : PROD | TEST
   FREQUENCY : RARE
   OWNER     : your name
   VERIFIED  : 2026-08-14
   TICKET    : OTM-4821 (optional)
   NOTES     : anything the next reader needs to know
------------------------------------------------------------ */

06The master index

One markdown or spreadsheet file at the root of the library — INDEX.md — that lists every query with the fields that folders and filenames can't express. This is what you actually search when the question is "usage," not "location."

FileModuleTaskUsed forFrequencyLast verified
rate_FIX_missing-fuel-surcharge…RateFIXBackfills surcharge on lanes missing a rate componentRare2026-08-14
shipment_MONITOR_unplanned-24h…ShipmentMONITORFlags shipments unplanned after 24h of order releaseDaily2026-08-30
tender_REPORT_carrier-accept-rate…TenderREPORTMonthly carrier acceptance-rate rollup for ops reviewMonthly2026-08-01

Update this file whenever you add, retire, or re-verify a query. It's the only place multi-module and cross-cutting queries need to be listed twice — the file itself only lives in one folder.

07Finding a query fast

With headers in place, a plain-text search across the whole library beats browsing folders once the collection grows past a couple dozen files.

terminal
# every query touching a given table
grep -ril "RATE_OFFERING" otm-sql/

# every MONITOR query, regardless of module
grep -ril "TASK TYPE *: *MONITOR" otm-sql/

# anything not re-verified in the last 6 months (needs `fd`/`find` + header date)
grep -rl "VERIFIED" otm-sql/ | xargs grep -L "2026-0[3-9]\|2026-1"

If the library is shared with a team, the same header fields drop straight into a spreadsheet with almost no reformatting — useful the day someone asks "do we already have a query for this?" before writing a new one.

08Keeping it alive

!

A structure only stays useful if new files are born into it. The moment a query gets saved as "test2_final.sql" on the desktop, the whole system starts leaking. Make the header template a saved snippet in whatever editor you write SQL in, so filling it in costs nothing.

Retire, don't delete

Move to _archive/

Superseded queries move to _archive/ with their original name intact — cheaper than deleting, and searchable if a report ever needs to be reproduced.

Review quarterly

Re-verify FIX and MONITOR

Table and column changes in an OTM upgrade break exactly these two tag types most often. A short quarterly pass through the index catches drift early.

One library, not per-project

Resist forking by client

If the same library serves multiple environments or clients, add an ENV or client column to the index rather than duplicating the whole folder tree.
